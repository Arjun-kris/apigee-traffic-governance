# Apigee Global Gateway Traffic Governance

A production-oriented Apigee X / Apigee hybrid project for applying centralized,
environment-level traffic governance to an existing API estate **without editing
every API proxy and without changing backend services**.

The implementation uses a **PreProxy Flow Hook** as the environment-level
attachment point, a **Shared Flow** as the reusable governance engine, an
**environment KVM** as the control plane, and **targeted per-proxy SpikeArrest**
for runtime enforcement.

> **Default behavior is safe:** the supplied configuration starts in `monitor`
> mode. No API is throttled until you explicitly list it and switch the
> configuration to `enforce`.

---

## Why this project exists

Large Apigee environments often contain hundreds of proxies that already have
their own authentication, validation, quota, SpikeArrest, and business logic.
Editing all of them just to introduce platform-level cost/traffic governance
creates unnecessary deployment risk.

This project adds a governance layer above those proxies:

```text
Client
  |
  v
Apigee Environment
  |
  v
PreProxy Flow Hook
  |
  v
global-gateway-governance Shared Flow
  |-- KVM configuration
  |-- proxy identification
  |-- bypass decision
  |-- targeted rate decision
  `-- SpikeArrest
  |
  v
Existing API Proxy      <-- unchanged
  |
  v
Existing Backend        <-- unchanged
```

A Flow Hook makes a Shared Flow run at the same lifecycle point for every proxy
deployed to an environment. The Shared Flow therefore remains independently
implemented and deployed rather than being inserted into the code of each proxy.

---

## What it does

The project provides:

- zero-touch integration with existing proxies through `PreProxyFlowHook`,
- centralized environment configuration using KVM,
- `off`, `monitor`, and `enforce` modes,
- exact-name critical API bypass,
- targeted proxy-by-proxy rate configuration,
- per-proxy SpikeArrest grouping using `apiproxy.name`,
- fail-open behavior when governance configuration is missing or invalid,
- scripts to create/update KVM configuration,
- scripts to import/deploy the Shared Flow,
- guarded Flow Hook attach/detach scripts,
- Analytics query example,
- local validation and JavaScript unit tests,
- GitHub Actions validation,
- production runbook and troubleshooting documentation.

This project **does not** replace existing proxy-specific policies.

---

## Important design boundary: no fake "global Quota"

This repository intentionally does **not** claim to implement one native Apigee
Quota counter shared across hundreds of independent API proxies.

The project instead separates two jobs:

1. **Gateway-wide observation** — Apigee Analytics is used to understand total
   traffic and identify high-volume proxies.
2. **Targeted runtime control** — SpikeArrest is applied only to explicitly
   selected proxies.

This avoids allowing one noisy API to consume a single blanket gateway rate
bucket and unintentionally block unrelated critical APIs.

## Prerequisites

You need:

- an Apigee X or compatible Apigee hybrid organization,
- an existing environment such as `dev`, `test`, or `prod`,
- `gcloud` authenticated to the Google Cloud account that can administer Apigee,
- `curl`,
- `zip`,
- Python 3,
- Node.js 20+ only for the included local JavaScript unit tests.

Authenticate:

```bash
gcloud auth login
gcloud auth application-default login
```

The deployment scripts use:

```bash
gcloud auth print-access-token
```

Your account/service account needs the Apigee permissions required to manage
Shared Flows, deployments, KVMs, and Flow Hooks. Flow Hook attachment is a
high-impact administrative action.

## 1. Clone and configure

```bash
git clone https://github.com/YOUR_USERNAME/apigee-global-gateway-governance.git
cd apigee-global-gateway-governance

cp .env.example .env
```

Edit `.env`:

```bash
ORG=my-apigee-org
ENV=dev
SHAREDFLOW=global-gateway-governance
KVM_NAME=GLOBAL_GATEWAY_GOVERNANCE
CONFIG_FILE=config/governance-config.example.json
```

`.env` is ignored by Git.

---

## 2. Understand the configuration

Example:

```json
{
  "mode": "monitor",
  "throttleProxies": {
    "orders-api": "200ps",
    "catalog-api": "150ps"
  },
  "bypassProxies": [
    "payment-api",
    "authentication-api",
    "health-api"
  ]
}
```

### `mode`

| Mode | Behavior |
|---|---|
| `off` | No governance enforcement |
| `monitor` | Evaluate only; never run this project's SpikeArrest |
| `enforce` | Run SpikeArrest only for proxies explicitly listed in `throttleProxies` |

### `throttleProxies`

Maps the exact Apigee proxy name (`apiproxy.name`) to a SpikeArrest rate.

Valid rates:

```text
50ps
200ps
3000pm
```

There is deliberately **no default global rate**.

### `bypassProxies`

Exact proxy names that must never receive this additional governance
SpikeArrest. If a proxy appears in both lists, bypass wins.

## 3. Validate locally

```bash
./scripts/validate.sh
```

or:

```bash
make validate
```

Validation checks:

- all bundle XML is well formed,
- policy manifest matches policy files,
- Shared Flow steps reference real policies,
- config JSON is valid,
- shell scripts parse,
- JavaScript decision-engine tests pass when Node is installed.

Expected test output includes:

```text
PASS monitor never enforces
PASS enforce targets explicit proxy
PASS unlisted proxy is monitor-only
PASS bypass wins over throttle mapping
PASS off disables enforcement
PASS invalid JSON fails open to monitor
PASS invalid rate fails open for that proxy
```

## 6. Upload configuration in monitor mode

First validate it:

```bash
python3 tools/validate_config.py config/governance-config.example.json
```

Then upload it:

```bash
CONFIG_FILE=config/governance-config.example.json \
  ./scripts/put-kvm-config.sh
```

Do this **before** attaching the Flow Hook.

The runtime KVM policy caches the value for 60 seconds, so control-plane changes
may not be visible to every request immediately.

## 8. Verify the environment before attaching

List Shared Flow deployments:

```bash
./scripts/list-sharedflow-deployments.sh
```

List existing Flow Hooks:

```bash
./scripts/get-flow-hooks.sh
```

**Do not overwrite an existing PreProxy Flow Hook owned by another platform
control.** Apigee allows one Shared Flow per hook. If one already exists, merge
this governance logic into that Shared Flow or have the existing Shared Flow
call a governance Shared Flow.

## 9. Attach the PreProxy Flow Hook

This step affects every proxy deployed to the environment.

```bash
./scripts/attach-flow-hook.sh
```

The script requires you to type:

```text
ATTACH
```

For CI/CD where change approval is already handled externally:

```bash
YES=true ./scripts/attach-flow-hook.sh
```

Keep the KVM in `monitor` mode at this stage.

## 10. Runtime decision flow

For every request:

```text
Read KVM
  |
  v
Get apiproxy.name
  |
  +-- mode=off ------------------------------> allow
  |
  +-- proxy in bypassProxies ----------------> allow
  |
  +-- proxy not in throttleProxies ----------> allow
  |
  +-- invalid/missing rate ------------------> allow
  |
  +-- mode=monitor --------------------------> allow
  |
  `-- mode=enforce + valid explicit rate
          |
          v
     SpikeArrest
          |
          +-- under rate --------------------> allow
          |
          `-- over rate ---------------------> HTTP 429
```

The JavaScript policy writes flow variables useful in Trace/Debug:

```text
governance.mode
governance.proxy
governance.bypass
governance.targeted
governance.rate
governance.rate.valid
governance.enforce
governance.decision
governance.config.valid
governance.config.error
```

## 11. Why the SpikeArrest has an Identifier

The policy contains:

```xml
<Identifier ref="governance.proxy"/>
<Rate ref="governance.rate">100ps</Rate>
<UseEffectiveCount>true</UseEffectiveCount>
```

`governance.proxy` is populated from `apiproxy.name`.

This intentionally groups rate limiting by proxy name, which is important
because the policy is running from one environment-level Shared Flow.

`UseEffectiveCount` is enabled for distributed rate counting, as recommended in
current Apigee SpikeArrest guidance for Apigee organizations.

## 12. Move from monitor to enforce

Do not make this your first production step.

A sensible rollout is:

```text
dev
  -> test
     -> staging
        -> production monitor
           -> one non-critical proxy
              -> small controlled set
                 -> broader targeted enforcement
```

To change mode and upload the config:

```bash
./scripts/set-mode.sh enforce config/governance-config.example.json
```

Return to monitor:

```bash
./scripts/set-mode.sh monitor config/governance-config.example.json
```

Emergency off:

```bash
./scripts/set-mode.sh off config/governance-config.example.json
```

## 13. Analytics and reporting

The runtime governance layer should not try to become an accounting database.

Use Apigee Analytics to answer questions such as:

- which proxy receives the most requests,
- request volume trends,
- average response time,
- error rate,
- 429 rate,
- before/after traffic volume.

An example asynchronous Analytics query payload is in:

```text
config/analytics-query.json
```

Submit it:

```bash
./scripts/query-usage.sh
```

Asynchronous report jobs are appropriate for large data volumes or long time
ranges. Real-time Custom Reports are useful for interactive operational views.

### Suggested reports

1. message count by API proxy,
2. traffic/TPS trend by API proxy,
3. average total response time by API proxy,
4. 4xx/5xx response distribution,
5. 429s by API proxy,
6. top traffic-generating consumers/apps where those dimensions are available,
7. before-vs-after governance comparison.

### Billing correlation

Apigee Analytics measures API usage and performance. Actual cloud charges should
come from Google Cloud Billing/FinOps data. Correlate the two for cost analysis;
do not claim that the Shared Flow itself calculates the exact cloud invoice.

## 14. Smoke testing

Set an existing non-production API URL:

```bash
export TEST_URL="https://api.example.com/test"
```

Send ten requests:

```bash
./scripts/smoke-test.sh
```

For a controlled SpikeArrest test:

1. add that non-production proxy to `throttleProxies`,
2. choose a deliberately low test rate,
3. upload the config,
4. set mode to `enforce`,
5. send a burst,
6. verify expected 429s,
7. return to `monitor`.

Never perform burst testing against a production API without authorization.

## 15. Emergency rollback

Fastest application-level rollback:

```bash
./scripts/set-mode.sh off config/your-prod-config.json
```

Strongest environment-level rollback:

```bash
./scripts/detach-flow-hook.sh
```

See [docs/RUNBOOK.md](docs/RUNBOOK.md) for the full production procedure.

## 17. Known limitations

- A Flow Hook has environment-wide blast radius.
- Only one Shared Flow can be attached to each Flow Hook in an environment.
- KVM configuration is cached; changes are not instantaneous.
- SpikeArrest is operational traffic control, not a monthly business quota.
- This implementation uses exact proxy names, not wildcard/regex matching.
- Existing proxy policies continue to apply, so a request can be rate-limited by
  both this governance layer and a proxy's own policies.
- Analytics entitlement and report APIs vary by Apigee subscription / PAYG
  configuration.
- This project does not calculate exact Google Cloud billing charges.
